# 博客内容整理

## 1. 确认素材与当前实现

- 读取根目录 `AGENTS.md`、`CONTEXT.md`、目标内容及其用户改动；保留用户已有工作。用户给了素材就开始整理，未给素材时检查明确相关的草稿；多个候选无法确定时询问目标。
- 读取 [内容与呈现参考](references/content-and-mdx.md)。按任务涉及的集合、标题和组件，重读其中列出的 schema、页面或组件源码；参考文件是导航与已知陷阱，当前源码决定实际行为。
- 以 `src/content/config.ts`、`src/content.ts`、路由与渲染配置确认实现，以 `CONTEXT.md` 和相关 ADR 确认约束。`README.md`、功能全览与组件指南含历史内容，示例须先核对。遇到实现与 ADR 的差异，在交付说明中指出，保持本次工作在内容范围内。
- 先确认内容归属、最终文件路径、现有日期、草稿状态，以及哪些内容是作者观点、事实、引文或未完成提纲。步骤完成标准是这些项目均有依据，而非只读了一篇示例。

## 2. 锁定原意与补写边界

- 在内部记下受保护事实：人物、数字、时间、代码、术语、因果关系、确定程度、引文与出处。保留第一人称、作者的犹豫和个人语气。
- 用户要求整理时，可调整标题层级、段落顺序、衔接和组件排版；保留各项有效观点。大段删减、技术结论变化与新增论证，在交付说明中分别列出。
- 用已有素材补足说明；新增技术事实先查证对应代码或一手资料，保留可追溯出处。把作者的直觉写成作者的直觉，不能改成普遍结论。
- 遇到缺失步骤、残缺列表、矛盾机制或没有来源的引文，先完成独立的排版工作，再明确标记待补内容。知识不足以支撑的段落保持草稿，不凭空补成定稿。

## 3. 适配内容契约与阅读结构

- 从参考中的集合规则选择目录与 frontmatter。新内容默认 `draft: true`；既有内容保留发布状态，明显残缺且尚未发布的素材设为草稿并说明。
- 保留既有 `date`；新增内容使用用户给定日期，否则用当前环境日期并说明。已有内容实质更新才填写 `updated`，不以更新时间覆盖初次日期。`author` 与 `cover` 只填有依据的值。
- 写有信息量的 `description` 和贴合主题的标签，优先复用已有标签；摘要用于搜索、RSS 和分享，不是页面正文导语的替代品。
- 技术文和娱乐单篇正文保留一个 Markdown H1；集合与子项正文从导语或 H2 开始，因为页面已经生成 H1。
- 用 H2 划分主线、H3 展开分支、H4 承载必要细节。目录只收录 H2–H4；保持层级连续，避免仅有 H3 的提纲、为一句话建章节或手工再加目录编号。
- 首屏交代主题与适用范围。每段推进一个意思，步骤用有序列表，平行信息用无序列表，比较或字段映射才用表格。连续论述保持段落，不强制套“背景—原理—总结”模板。
- 标题写清这一节讲什么；检查目录本身是否能帮助读者定位。减少长标题、重复“总结”、整段粗体与密集分割线，保留作者有作用的表达。

## 4. 按阅读用途选 MDX 表达

- 先用普通 Markdown；仅在引文批注、补充说明、读音、视频、图片说明或实际操作需要时选择参考中已有的元素或组件。
- 核对每个 import、prop、正文 slot 与资源路径。把主线留在可直接阅读的正文里，补充材料再放 `<details>`；交互工具必须有输入说明和结果解释。
- 区分普通引用、`Quote` 与 `MarginNote` 的用途。使用 `MarginNote` 时保留来源文字与作者判断的界线，核对现有示例和源码；它已用于本站，但尚未列入 ADR-0003 的正文白名单，沿用时说明此差异。
- 正文不用页面骨架组件。新增交互能力、修改渲染插件或组件属于站点开发，先给出具体需求与影响，不把它混进内容润色。
- 让关闭 JavaScript、无法播放视频、折叠未展开的读者仍能读懂核心观点。`llms-full.txt` 输出原始 MDX，重要解释也应有普通文字。
- 完成标准是每个特殊表达都有明确阅读用途、现有实现依据和可编译语法；“可玩性”不构成堆组件的理由。

## 5. 验证与交付

- 分三遍回读：先逐项核对原意和事实，再检查中文与段落衔接，最后核对标题目录、强调密度、折叠内容与资源说明。技术机制变化单独说明，不能用润色掩盖。
- 若修改 MDX，执行 `npm run build`，确认 schema、import 和 MDX 编译通过。生产构建过滤草稿，另用本地 `npm run dev` 打开草稿对应 URL，检查开发渲染。
- 检查编译后的标题数量和目录锚点；复杂 JSX 内 Markdown 检查实际 HTML，不能只看构建成功。新增组件布局时检查桌面及窄屏；新增交互时操作一次并检查浏览器错误。只改文字时不扩大成站点全量 UI 审查。
- 草稿在生产路由、搜索索引、RSS、sitemap 和 `llms-full.txt` 中均应缺席。集合同时检查父级草稿状态、子项关联、排序和前后导航。
- 运行 `git diff --check`，检查最终 diff 只包含授权的内容与规则改动。不自动提交、推送或部署；用户明确要求时再执行相应动作。
- 简洁交付文件链接、内容归属、状态、主要调整、验证结果与待作者补充的具体项。构建通过只说明技术兼容，不说明技术观点已被证实，也不说明内容已发布。
