# 编辑任务与检查工具

## 按用户任务选择处理方式

| 请求 | 执行动作 | 完成标准 |
| --- | --- | --- |
| 新建内容、把素材整理成博客 | 确定读者、主题和集合；选模板，替换全部占位内容；保留素材来源 | 得到真实 `.mdx` 草稿，可本地打开 |
| 润色、优化阅读体验 | 核对原稿观点；改善句子、段落、标题和强调；按明确用途选组件 | 有效观点均保留，说明实质变化 |
| 补写、完善提纲 | 列出缺失的论证、例子、机制或出处；先补有依据的部分 | 新增事实有出处，未解决的问题具体列出 |
| 检查是否符合文章规范 | 只读检查原文、运行脚本、核对 Schema 和实际呈现 | 区分错误、编辑建议和待验证项目，不改文件 |
| 准备定稿 | 清理作者已经解决的占位说明，核对来源、资源和元数据 | 达到可发布质量，草稿状态按用户授权处理 |

“继续开发 Skill”更新 Skill 本身，不自动扩写仓库里的其他草稿。未指定目标时，先看现有改动及明确相关内容；存在多个同等候选才询问。

## 模板

从 skill 的 `assets/` 复制对应文件，分别为 `tech.mdx`、`entertainment.mdx`、`series.mdx`、`chapter.mdx`。模板只规定元数据和是否需要 H1，不强制内容结构。

- 创建前检查目标路径，已有文件就原地整理，避免覆盖或同稿多份。
- 日期 `2000-01-01`、`待填写…`、`replace-with-series-slug` 和注释都必须替换；新日期来自用户或当前环境，已有日期保留。
- 新内容维持 `draft: true`。集合子项检查父集合 slug 和 order；同集合的 URL 使用子项文件名末段，避免重复末段文件名。
- 根据素材写摘要、选标签。没有实际图片、附件或视频时省略组件，模板不填虚构资源。

## 只读检查

在仓库根目录运行：

```bash
node .trae/skills/blog-writing/scripts/check-content.mjs src/content/tech/guoqing-weekly.mdx
node .trae/skills/blog-writing/scripts/check-content.mjs --all --json
```

可以一次传多个文件。`--help` 查看参数；`--strict` 将建议也计入失败。默认错误退出码为 1，参数错误为 2，只有建议时退出码为 0。脚本不写文件、不发网络请求、不执行文章里的 JavaScript，也不会自动发布。

检查覆盖：

- YAML/MDX 能否解析、基础字段类型、单篇/集合标题数量、标题跨级与重复。
- 本地组件 import 是否存在、正文是否误用页面骨架、源码中可识别的必填 prop 是否缺失。
- 静态 Pinyin 参数数量、默认关闭工具的展开条件。
- 根路径图片/附件是否存在、资源大小、替代文字、代码围栏语言和当前不支持的提示/高亮/Mermaid 写法。
- 父集合是否存在、order 是否重复，以及父集合草稿对子项的影响。

检查器是编辑辅助，不是平台 Schema 的副本。它对元数据规则的有限检查基于当前契约；新增字段时先读 `src/content/config.ts`，建议中的“未知字段”不等于 Schema 错误。Props 只识别当前组件里的 interface 必填声明；动态表达式、spread、外部组件映射和间接资源引用需手工核对。

它不会验证远程资源可访问性、相对路径图片的 Astro 管线、语法高亮语言的实际效果、正式站点路由与锚点、图像来源规则、全部日期业务约束或技术事实。用 `npm run build` 检查真实 Astro Schema/import/编译；用开发预览检查草稿和交互。

旧内容可能有标题重复等历史问题。检查全库用于发现这些问题，不把“全库无建议”当作本次完成条件；只修用户指定范围，新旧问题分别说明。

## 编辑回读与交付

三遍独立检查：

1. 对照原稿，检查观点、技术关系、数字、时间、出处、代码和确定程度；补写内容逐项标明依据。
2. 连续阅读，检查主线是否清楚、每段是否推进意思、长句是否有自然停顿；保留口吻，不为了整齐把个人思考改成教程。
3. 看目录和实际页面，检查标题定位、过密强调、移动端表格、引用批注、折叠补充、资源与操作说明。

组件选用说明只写有必要的决定，例如“将背景材料放入折叠，核心步骤保留在正文”。待补项目指出具体缺口，例如“工具结果如何回到模型、退出条件是什么”，不用“需要更完整”代替。

最终交付按任务大小压缩为：文件链接、内容状态、主要调整、验证结果、仍需作者提供的素材。检查任务先列错误和位置，再列建议；新增事实或改变技术结论单独说明。构建成功和脚本通过都不代表事实正确，也不代表已发布。
